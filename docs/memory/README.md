# 进度记忆更新流程（轻量版）

## 适用时机
- 每个阶段完成并测试通过后。
- 每个组件完成并测试通过后。

## 必做步骤
1. 在 `docs/memory/components-progress.md` 的“已完成组件”追加一行完成记录。
2. 在“测试状态”更新该组件最新结果，并补齐测试证据（命令、日志或 CI 链接）。
3. 在“兼容性备注”写明对齐状态与差异，不允许空白。
4. 在“下一组件队列”把下一个要做的组件提升到最高优先级，并写清前置条件与 DoD。
5. 在文件末尾按模板追加一段详细记录，确保下次可直接续做。
6. 组件测试通过后，必须同步更新 `apps/playground` 展示页，让最新完成的组件在本地示例中可见。
7. 禁止把根目录 `src/` 作为 showcase 目标；本地展示页只认 `apps/playground`。
8. 若 showcase 未更新，不得将组件标记为真正完成。
9. **阶段完成时必须新建“下一阶段计划文件”**（`docs/implementation/stage-plans/*.md`），并在 `components-progress.md` 的“下一阶段开发规划”中登记路径。

## 记录原则
- 只记录“已验证事实”，不写猜测。
- 未有测试证据不得标记“完成”。
- 如果发现 API 不合理或需求不清晰，先提问再推进，不自行假设。
- 组件库优先复用公共能力，避免引入一次性实现与废代码。
- 没有“下一阶段计划文件”的阶段，不算真正完成。

## 下一阶段计划详细度硬标准（每次都必须满足）
后续每次制定“下一阶段计划文件”（`docs/implementation/stage-plans/*.md`）时，至少包含：
1. 目标与边界：做什么、不做什么。
2. 产物清单：明确到文件级（要新增/修改哪些文件）。
3. 执行顺序：组件/任务依赖关系与先后顺序。
4. 接口契约：核心 props / emits / slots / methods 约束。
5. 测试矩阵：每个组件至少列出关键行为测试点。
6. 子代理任务卡：scope、禁止项、DoD、交付物。
7. 阶段门禁：`test/typecheck/build/docs` 等验收命令与通过标准。
8. 风险与疑点：必须显式列出“需向用户确认”的项，禁止自行猜测。

未达到以上标准的“下一阶段计划”，视为无效计划，需要重写。
